# Claude Code 프로젝트 피드백 (2026-11-04)

검토자: Claude Code (`claude-opus-5-5`). 범위: 저장소의 기획 문서 전체. 게임 코드·빌드·플레이는 존재하지 않으므로 검토 대상이 아니다.
이 문서는 의견이다. 사용자 승인·테스트 통과·공식 근거로 취급하지 않는다.

## 1. 요약

기획 품질은 높다. 그러나 문서만 있고 게임 코드는 없다. 가장 큰 문제는 **사용자가 원하는 게임(해킹 시뮬레이터)과 문서가 그리는 게임(보안 교육형 조사·복구 게임) 사이의 방향 차이**다. 그다음 문제는 1인 개발에 비해 큰 범위다.

## 2. 현재 상태

- 커밋 2개, Markdown 19개(약 2,000줄). `project.godot`와 게임 코드는 없다.
- 개발 환경에 Godot 4.7 stable이 설치돼 있다(`/opt/homebrew/bin/godot`). 바로 기술 검증을 시작할 수 있다.
- 기존 독립 검토(`gpt-6.1-sol / xhigh`)의 판정은 문서 계약 기준 READY다.

## 4. 문제점과 제안

### 4.1 방향 차이 (가장 중요)

- 사용자 요청은 "해킹 시뮬레이터 게임"이다. 문서는 학습 평가·전이 문제·복구 업무 중심이고, 장르 특유의 긴장 연출은 대부분 "기본 끔" 또는 "선택 모드"로 밀려 있다. 첫 미션 M01도 정비 업무에 가깝다.
- 이번 세션에서 사용자는 쾌감형(A안)을 골랐지만, 그 방향으로 문서를 고치는 작업은 중단했고 원래 문서로 되돌렸다. **방향 결정은 아직 문서에 반영되지 않았다.**
- 제안: 구현을 시작하기 전에 방향을 문서에 확정한다. 교육형을 유지하면 지금 문서를 그대로 쓰고, 쾌감형으로 가면 `PROJECT_PLAN.md`·`CURRICULUM.md`·`DESIGN.md`를 다시 써야 한다.

### 4.2 범위가 1인 개발에 크다

- 3D 작업실, Windows/macOS/Linux, 6개 언어, OST 7곡, 메인 24 + 선택 4 미션. 문서 자체 추정으로도 18~30주(360~900시간)다.
- 3D 작업실이 P0에 들어가 있다. 핵심 루프는 2D 가상 OS 안에서 일어나므로 3D는 초기 위험만 늘린다.
- 제안: P0에서 3D를 빼고 2D 데스크톱 + 터미널 + 미션 하나로 줄인다. 3D·다국어·OST는 시제품이 재밌다고 확인된 뒤 붙인다.

### 4.3 문서 분량 대비 정보가 적다

- "기획 단계다", "NOT_RUN", "~하지 않는다" 같은 면책·부정 문장이 여러 문서에 반복된다. 같은 내용이 README·HANDOFF·AGENTS·PROJECT_PLAN에 겹쳐 있다.
- 제안: 면책은 한 곳(README "현재 상태")에만 두고, 나머지 문서는 결정과 계약만 남긴다.

### 4.4 시제품 단계에 비해 설계가 무겁다

- 증거별 의존 버전(`dependency_versions`·`claim_phase`), 지연 작업 큐(`pending_jobs`), `content_hash` 호환표, `LearningState` 분리가 이미 필수 계약처럼 적혀 있다.
- 문서 스스로 "필요할 때 추가"라고 하지만, 계약에 적혀 있으면 첫 구현자가 다 만들게 된다.
- 제안: 이 항목들을 "MVP 이후 검토"로 옮기고, P1에는 상태·명령·판정·저장 왕복만 남긴다.

### 4.5 머지 게이트가 없다

- 전역 운영 규칙은 프로젝트별 `tools/gate.sh`와 CLAUDE.md의 `SENSITIVE_PATHS`를 요구한다. 둘 다 없다.
- 제안: 코드를 시작할 때 `tools/gate.sh`(콘텐츠 검증 + headless 테스트 + 금지 API grep)와 `SENSITIVE_PATHS`(저장·판정 코어)를 함께 만든다.

### 4.6 문서 정합성 (사소함)

- `CLAUDE.md`는 "Claude 추가 호출은 하지 않는다"고 적혀 있지만, 이번 세션은 Claude Code로 저장소를 검토했다. 실제 사용 방식에 맞게 갱신이 필요하다.
- 문서의 Codex 모델명(`gpt-6.1-sol`)과 전역 규칙의 모델명(`gpt-5.6-sol`)이 다르다. 실제 사용 값을 확인해 한쪽으로 맞춘다.
- `docs/references/`는 빈 폴더다. 쓸 계획이 없으면 지운다.

## 5. 추천 순서

1. 방향(교육형/쾌감형)을 확정하고 `PROJECT_PLAN.md` 결정 기록에 남긴다.
2. 가칭을 정한다. 이번 세션에서 사용자는 "심야접속"을 골랐다. 아직 문서에 반영하지 않았고, 상표·스토어 중복 확인도 하지 않았다.
3. P0를 줄인다: 3D 제외, 2D 데스크톱·터미널·한글 IME·저장 왕복.
4. 미션 하나를 끝까지 연결하고 제작 시간을 잰다.
5. 재미가 확인되면 범위를 넓힌다.

## 6. 이번 세션 기록

- 저장소 분석 후 방향 선택지를 제시했고, 사용자는 쾌감형(A안)과 가칭 "심야접속"을 골랐다.
- 쾌감형으로 기획 문서를 고치던 중 Claude 쪽 안전 분류기에 의해 응답이 여러 번 중단됐다. 사용자 결정에 따라 모든 문서 변경을 되돌렸다. 저장소의 추적 파일은 커밋 `437118c`와 같다.
- 게임 코드·시제품은 만들지 않았다. 커밋도 하지 않았다.
