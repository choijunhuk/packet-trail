# Hacknet 패키지 구조 참고 — 2026-11-04

출처는 사용자가 대화에 제공한 `Hacknet.app / Contents 정적 분석` 보고서다. 원 보고서가 관찰·도출·추론·미확인을 나눴으므로 여기서도 그 범위를 유지한다. 이후 추가 구조 설명은 사용자가 제공하는 자료를 기준으로 참고하며 설치본을 계속 조사하지 않는다.

## 1. 전달받은 분석과 직접 대조한 범위

| 구분 | 내용 |
|---|---|
| 보고서의 관찰 | Mono 런처, FNA 17.2.0.0/Steamworks.NET 참조 .NET 게임 어셈블리, XML·텍스트·XNB·CEF 구성 |
| 보고서의 정적 연결 | Terminal→명령 디스패치→Computer/Folder/FileEntry, XML 컴퓨터/목표 로더, 완료 검사와 후속 행동, 로컬·Steam 저장 계층 |
| 이번에 제한적으로 대조 | 실행 파일 크기·SHA256·plist 식별자, FNA/Mono 런처/CEF/대표 XML 경로 존재와 XML 크기 |
| 대조하지 않은 것 | 전체 인벤토리·IL/타입/메서드의 의미·FNA 참조 버전·외부 효과의 활성화·실제 플레이·모든 미션·빌드 재현 |

식별 대조 결과:

- `Hacknet.exe`: 1,477,120바이트, SHA256 `b4d73a532ac56483c386047cdea0ce5dbcc18c84678f97765c1d196915397570`.
- Bundle ID `com.hacknet-os.Hacknet`, 실행 파일 이름 `Hacknet`, plist 표기 `1.0`/`1`.
- FNA DLL·Mono 런처·CEF 경로가 존재하고 대표 `ExampleMission.xml` 크기는 17,470바이트로 전달된 보고서와 일치했다.

이 확인은 보고서가 가리킨 설치본의 식별을 뒷받침한다. 모든 IL 결론을 별도로 재현한 결과는 아니다. 앱·런처·어셈블리를 실행하거나 디컴파일 도구를 설치하지 않았고, 별도 JSON 증거 묶음은 열람하지 않았다. 플리스트의 버전 문자열도 현재 OS 호환성의 증거가 아니다.

## 2. 새 게임에 가져올 구조적 원리

```text
터미널/앱 입력 → 등록된 명령·행동 처리 → 가상 컴퓨터/파일/서비스
                                      ↓
                    목표 검사 → 사건 후속 행동 → 저장 스냅샷
```

1. **규칙과 콘텐츠를 분리한다.** 노드·파일·메일·목표는 데이터로, 접근·권한·명령의 의미는 공통 코드로 둔다.
2. **명령은 가상 상태를 바꾼다.** 화면의 성공 문구만으로 침투가 성립하지 않고 동일한 Computer/파일/서비스 상태에 반영돼야 한다.
3. **작은 목표·완료·후일담을 연결한다.** M01 자료 회수와 다음 노드 공개부터 완주시키고 콘텐츠를 확장한다.
4. **저장 어댑터는 가상 규칙과 나눈다.** 첫 버전은 로컬 저장 왕복에 집중하고 Steam Cloud는 별도 제품 결정으로 둔다.
5. **원작과 같은 형식을 강요하지 않는다.** 심야접속의 콘텐츠는 Godot에서 검증하기 편한 자체 JSON/리소스 계약을 쓴다. XML·XNB·Mono/FNA를 따라야 할 이유는 없다.

## 3. 그대로 가져오지 않을 것

보고서의 명령 Thread 생성은 원작의 구현 관찰이다. 새 게임은 UI·상태 전이가 단순한 순차 처리로 충분한지 먼저 검증한다. 백그라운드 작업이 필요하기 전 원작의 스레드 구조를 복제하지 않는다.

원작에 CEF·실제 이메일 전송 호출이 있다는 관찰은 ‘원작의 모든 기능이 내부 가상 동작’이라는 일반화를 반박한다. 심야접속이 실제 외부 shell/네트워크를 게임 입력에 연결하지 않는 것은 **우리의 제품 경계**다. 게임 속 브라우저는 내부 페이지 모델부터 만든다.

관리형 IL과 콘텐츠 문법은 원본 C# 프로젝트를 확보했다는 뜻이 아니다. 원작 타입·토큰·파일 수를 새 코드의 설계나 완성도 증명으로 쓰지 않는다. 원작 코드·XML·음원·이미지·XNB는 이 저장소로 복사하지 않는다.

## 4. 상세 보고서에서 가져온 판정·저장 교훈

아래 항목은 [Claude 2차 피드백](../reviews/CLAUDE_FEEDBACK_20261104_R2.md)이 사용자 상세 정적 보고서를 요약한 내용이다. 이번 Codex 재검토에서 그 상세 원문·IL은 대조하지 않았고 원작 파일도 추가로 열거나 실행하지 않았다. 따라서 아래를 독립 재현한 원작 버그라고 주장하지 않는다. 원작 XML/코드를 저장소로 가져오는 대신 검증 가능한 새 설계 규칙만 적용한다.

| 보고서의 관찰 | 심야접속 계약 |
|---|---|
| 목표 목록이 비면 완료(true), 지원하지 않는 goal type은 오류 없이 건너뜀 | 콘텐츠 로더가 빈 `goals`·미등록 goal kind를 거절 ([기술 계약](../ARCHITECTURE.md) §4) |
| 저장은 `activeCheck`, 불러오기는 `activeChack`을 찾음. 일부 미션 설정은 저장에 들어가지 않음 | 정규화한 권위 지속 snapshot을 독립 기대값과 깊은 비교 (§10) |
| 파일 다운로드 목표는 이름이 아니라 내용으로 비교 | 목표 자료의 ID+불변 원본 데이터/허용 출처로 판정 ([M01](../CURRICULUM.md)) |
| 명령마다 대소문자·별칭 비교가 다르고, 공백 한 칸으로만 인자를 나눔 | 파서 규칙은 모든 명령에 같게, 별칭은 registry 한 곳 (§6) |
| XML `portsForCrack val`을 내부에서 `val-1`로 저장 | 콘텐츠 수치의 의미는 유지하고 검증 뒤 의미 보존 타입 정규화만 허용 (§4) |
| 완료 시 분기 초기화→다음 미션→종료 함수→저장 순서 | 미완료→완료 효과를 같은 커밋에 한 번 적용, 저장은 그 뒤 (§3) |
| 새 도구가 서버에서 복사해 오는 가상 실행 파일 | 도구 해금을 회수한 자료로 표현 ([화면 설계](../../DESIGN.md) §6) |
| 명령을 백그라운드 스레드에서 실행하고 예외를 출력 없이 소비 | P1은 메인 스레드 순차 처리, 실패는 명시적 오류 코드 (§3) |

## 5. P0/P1과의 연결

이 자료는 초기 구현에 실제 OS/컨테이너가 꼭 필요하지 않다는 설계를 뒷받침하는 선례다. P0의 터미널/입력, P1의 가상 상태·명령·자료 회수 목표·저장 왕복을 먼저 완성하는 순서는 유지한다. 상세 단계는 [개발 계획](../ROADMAP_AND_QA.md), 코드/데이터 책임은 [기술 계약](../ARCHITECTURE.md)을 따른다.
